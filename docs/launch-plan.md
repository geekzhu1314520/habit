# 上线方案与放行结论

日期：2026-10-01。范围：跑步工具 + 默认关闭的步行实验。**结论：生产上线 NO-GO；本地候选版本可以进入受控预发布验证。** 本轮未创建远程站点、未发布、未发送通知。

## 已实现的发布准备

- `VITE_WALKING_ENABLED`：仅精确字符串 `true` 开启，缺失或任何其他值关闭。
- 新类型为“步行”：每天自行确认完成，不设公里门槛或 streak；独立键 `walking-experiment:v1`，schema 为 `{schemaVersion:1, days:string[]}`。日期必须合法、唯一、不晚于今天；最多 10,000 天、原文最多 200,000 字符。损坏不覆盖；读写失败显示错误。
- 跑步继续使用 `running-tracker:v1`，无需迁移。关闭步行只隐藏入口，不删除已记录的步行数据；旧版跑步应用忽略该独立键。
- 开关为**构建时**开关，不是在线即时开关，修改环境变量后必须重新构建并发布。不是授权或保密措施。
- 开关责任角色：仓库维护者；具体上线值班人须在发布前确认。复审日 2026-10-15；全量开放后 14 天内决定移除开关或撤回实验。未复审不得擅自扩大开放。
- Netlify 配置：`netlify.toml`；输出目录 `dist`；默认 OFF。`public/_headers` 会进入构建产物，包含严格 CSP、HSTS、nosniff、禁止嵌入、权限禁用和缓存策略。
- `/health.json` 是静态存活探针，不能代替页面 JS、持久化和用户流程检查。

## Netlify 部署计划

采用手动上传已验证产物，避免这次准备工作直接触发生产发布。Netlify 支持部署完整 `dist`，并能重新发布保留的旧原子部署；手动部署不会代你运行构建。

1. 本地执行：

```sh
npm ci --ignore-scripts
npm run typecheck
npm run lint
npm run test -- --run --coverage
npm run test:e2e -- --project=chromium
VITE_WALKING_ENABLED=true HABIT_TEST_PORT=5175 npm run test:e2e -- --project=chromium e2e/walking.spec.ts
npm audit --registry=https://registry.npmjs.org
VITE_WALKING_ENABLED=false npm run build
```

2. 保存 OFF 产物和对应 Git SHA；确认 `dist/_headers`、`dist/health.json` 存在。向**独立预发布站点**上传 `dist`。Git 自动构建可使用仓库中的 netlify.toml；它固定 OFF，若要启用 beta，必须明确修改对应构建配置，不能以为 UI 环境变量一定覆盖文件配置。
3. 用测试浏览器在预发布地址完成：启用跑步计划 → 两次累计达标 → 刷新 → 编辑 → 删除 → 错误恢复。测试 header、404、HTTPS、控制台、缓存和性能。另用 ON 构建在隔离 beta 站点验证步行。
4. 全部未勾项解决后，上传 OFF 产物到固定生产站点；记录 deploy ID 和可恢复的基线。首小时每 5 分钟检查根页面与 health.json、页面 JS 和持久化流程。
5. 步行先在 beta 站点由维护者使用 24 小时，无新增错误或数据异常后再申请扩大范围。当前只有静态构建开关，**不支持同一站点按用户 5%/25% 分流**，不伪造百分比灰度能力。以后若需要同站点分组，先设计隐私与分流规则。

浏览器数据按来源隔离。localhost、预发布域名与生产域名之间不会迁移已有记录；改生产域名或端口会让数据看似消失，但旧来源数据仍在。第一版无导入导出，上线前必须告知用户。

## 监测与放量阈值

- 首次发布没有可用历史基线或错误预算，不能把它当作“预算充足”。先收集预发布与首日基线。
- 建议可用性目标 99.9%，30 天窗口；预算 >20% 可常规发布，0–20% 仅低风险慢速发布，耗尽则冻结功能发布。尚未实际采集这些指标。
- 两次连续健康检查失败、任何数据丢失/覆盖或安全问题：立即回滚。
- 新 JS 错误类型：暂停扩展；可复现并影响核心操作则回滚，不等待小样本百分比。
- 有足够样本后，错误率 >2 倍基线或 P95 >基线 50% 时回滚；低样本不使用比例制造确定性。
- 默认通过外部静态健康探针（不携带记录）、手动浏览器检查和用户反馈监测。不自动接入第三方错误 SDK；若需上报，先确认只传脱敏诊断而非本地运动数据。

## 回滚步骤

### 首选：恢复已保留的 OFF 部署

1. 暂停后续发布。Netlify 站点 Deploys 页面找到事先记录的 OFF/稳定 deploy ID，选择 **Publish deploy**。不要重建未知旧代码作为紧急回滚。
2. 确認固定生产 URL 返回稳定版本；检查 `/health.json`、根页面、JS/CSS 均为 200，且步行入口已消失。
3. 在原浏览器刷新，确认跑步记录、累计和日程仍在。不得清除 localStorage，也不得把实验键合并到跑步键。
4. 检查安全响应头与控制台；首小时继续观察。负责人向使用者说明影响和恢复状态，本轮未代发。

### 备用：构建关闭开关的修复版

```sh
VITE_WALKING_ENABLED=false npm run build
```

重新验证并上传 `dist`。这需要构建/上传时间，不承诺一分钟内完成。把环境变量设为 false 而不重新部署不会改变已发布 JS。

### 数据与首次发布限制

- OFF 或旧跑步版本不读取实验键，实验记录原样保留；以后重启 ON 可继续读取。
- 本轮无 schema 迁移，不需要数据库回滚。代码回滚不能修复已经被错误代码写坏的数据，因此数据完整性问题须立即停止发布并保留现场。
- 第一次发布尚无可恢复 deploy ID；必须先发布并保留稳定 OFF 基线，再考虑 ON。没有基线或回滚权限就是 NO-GO。
- 回滚目标 ≤5 分钟，但须演练后才能作为实测承诺。
